01设计原则与已定边界

目标不是“再造一个通用 agent 框架”，而是把微信这个高约束通道下的 personal agent 做扎实：消息碎片化、无 IDE、强隐私、需要主动触达、必须可审计。 因此内核可替换、能力可插拔、评估可对比。

Principle 01

通道优先，而非框架优先

以微信会话的回合、分片、异步通知、审批卡片为第一等公民设计运行时； 不把“某个开源内核的抽象”当成事实标准。

Principle 02

规则省流，Agent 兜底

高频、结构化的微信意图（状态、审批、切项目、记忆 CRUD、帮助）走零模型调用的规则引擎； 口语化、多步、需要澄清或规划的意图升级给管家 Agent。规则与 Agent 共用同一套治理和审计。

Principle 03

没有度量就没有演进

所有运行产出统一 TraceEvent；任务集、评分、回归晋级、人工复核构成闭环； 同一套评估组件同时驱动 WFXM 与 dsh-wfxm。

◆
已拍板的三条边界： ① 管家层采用“规则引擎 + Agent”双通道，任务层采用 pi 原生内核； ② 记忆统一走 RAG，但用户画像与项目信息分域隔离；③ 评估按 butler / task 分轨，共用 TraceEvent 与沙箱。
◆
明确保留的 v5 资产： ports / 六边形依赖方向 · policy-gate + approval-runtime + scoped-grant + secret-redact · acceptance harness（fixture LLM 驱动真实 HTTP） · 微信入站/媒体/分片 · Drizzle + Postgres 持久化与 Run 租约。
明确重写： 任务层采用 pi（已 vendor）· 管家层独立 Butler Runtime（规则 + Agent）· 记忆由 agent-rag 文本优先封装 · 轨迹与评估分轨。

02分层架构

自上而下七层 + 两条纵向支撑（治理、观测）。管家层与任务层分离：前者规则优先、Agent 兜底； 后者保留 pi 原生开发能力。

02A管家层：独立运行时（规则 × Agent 双通道）

管家层的第一职责是“理解微信消息并决定下一步”，不是把所有消息都送进大模型。 规则引擎处理可枚举、可校验、零副作用歧义的高频路径；只有低置信度、需要澄清、需要规划或多步工具编排时才升级给 Agent。

FAST PATH · RULE

规则引擎负责“省流”

规则用 TypeScript/JSON 声明：priority、match（正则/命令/槽位）、 action（回复/查询/委派/审批/记忆写入）、requires（项目、权限、状态）。 规则动作仍走同一 policy / approval 闸门，不能绕过治理。

  • 高频：/status、/approve、/project、/memory、/help
  • 可校验：待审批列表、最近任务、项目切换、预算与用量
  • 目标：规则命中率 ≥ 60%，且规则误判率 < 2%
SLOW PATH · AGENT

Butler Agent 负责“兜底”

触发条件：规则无命中、置信度低于阈值、槽位缺失且需要澄清、跨项目/多步请求、 需要生成 TaskBrief、或规则执行失败连续两次。Agent 只做“理解 + 编排 + 总结”，不亲自改项目代码。

  • 输出结构化 ButlerDecision：Reply / Ask / DispatchTask / Approve / Remember
  • 每次调用带用户画像 + 最近任务摘要，不注入无关项目内容
  • 可降级：Agent 超时/失败时回退到规则兜底话术 + 人工入口
◆
v0.1 已落地（最小可用）： ButlerRuntime（packages/runtime/src/butler/）实现规则 × Agent 双通道： 规则命中零模型调用（/help、/status、/tasks、 /new <目标>、确认 / 拒绝）；未命中时跑小型工具循环 （start_task / list_tasks / task_status）， 工具经 ButlerTaskPort 转发任务层，不感知 pi 内部实现； 每轮可经 ButlerMemoryPort 召回用户画像注入系统提示； summarize() 产出结构化会话摘要（summary / profile / facts）并投影到用户记忆。 已提供 createPiTaskPortAdapter() 把该端口适配到 PiTaskRunner： inline / detached 两种执行、项目 cwd 解析、审批转发与状态映射； 会话可经 DrizzleButlerSessionStore 落到 butler_sessions（迁移 0016）； 审批提示与卡片回传已就绪：buildApprovalNotice() 同时产出文本和按钮 payload， parseApprovalPayload() + handleApprovalCallback() 把「确认 / 拒绝」直接转发任务层且不经过模型。 装配层 createButlerAssembly() 已就绪： 现有 LLM adapter 经 Effect.runPromise 包成 ButlerModelPort， 项目根目录映射（BUTLER_V5_PROJECT_ROOTS）构建 PiTaskRunner → PiTaskPortAdapter，会话默认落 DrizzleButlerSessionStore。 记忆由 createButlerMemoryFromEnv() 注入：配置 BUTLER_V5_MEMORY_PATH + BUTLER_V5_OWNER_ID 时启用 agent-rag（JSON 文本存储，跨重启保留画像），未配置则自动关闭且不影响管家功能。 新运行时已挂到 POST /v1/wechat/butler/inbound（同为 shared-secret 鉴权， 支持 approvalPayload 卡片回调）；旧 /v1/wechat/inbound 在 butler-eval 对齐前仍是主链路。 长轮次上下文（P0）：只保留最近 12 轮原文，更早轮次折叠进滚动摘要 （windowTurns / maxSummaryChars），并按 maxPromptChars 硬预算继续折叠，摘要随会话落库。 召回策略（P1）：命中即注入、5 分钟内同查询走缓存； 召回为空且问句含指代（或过短）时用最近 6 条消息改写查询再召回一次， 仍为空则退回最近有效记忆，全部过程写入 trace。 仓库地图（P3）：任务层启动时生成紧凑目录树 （路径 + 每文件少量导出符号，默认上限 2500 字符、5 分钟缓存）， 注入 pi 任务的 system prompt，避免 Agent 先盲扫仓库； 显式声明不做符号索引 / 向量化，等 task-eval 证明必要性再上。 多轮评估（P4）：butler 轨新增「约束跨轮持续注入」与 「无关轮次不注入记忆、不触发改写」两类用例，driver 输出 memoryRecallTurns / rewrites 指标； gate 增加 butler 通过率阈值（默认 ≥ 90%）。 呈现层（P4.5）：所有用户可见文本统一经 butler/presentation.ts 出口：工具名中文化 （write → 修改文件）、任务状态中文化（paused → 等待确认）、 去除微信不渲染的 markdown、空回复兜底、按行长分片发送 （默认 1800 字符）。配套 golden 快照与不变量测试， 审批消息固定包含「目标 / 待执行 / 原因 / 下一步」。 当前 32 管家 + 4 仓库地图 + 7 入站 + 5 装配 + 9 路由 + 1 一致性测试通过， butler-eval 11/11；capability 单轮 34/40（85%，上一轮 31/40）。

03评估—反馈优化闭环

左侧是自动化主干，右侧是人工闸门。任何改进都必须以“同题复跑 + 回归集不退化”作为晋级条件， 避免凭感觉调参。

TRACK · BUTLER

butler-eval：管家层

评“理解得对不对、该不该用 Agent、该不该审批、记忆召回是否准确”，而不是评代码改得对不对。

  • 意图路由准确率、规则命中率、误升级率、不必要 Agent 调用率
  • 澄清质量、TaskBrief 完整度、任务委派成功率、结果总结忠实度
  • 用户画像召回率/精确率、过期记忆率、隐私泄露（必须为 0）
  • 单轮延迟 / token 成本 / 规则 shadow 对比
TRACK · TASK

task-eval：任务层

评“能否在真实仓库里读、改、跑测试、按预算完成”，以工作区与测试结果为准，不以自述为准。

  • 工具成功率、测试通过率、patch 质量、工作区断言
  • 工具预算、轮次、耗时、审批时序（先审批后写入）
  • 长任务恢复、跨轮上下文、失败后自我修复
  • 项目记忆检索有用性、项目约定遵循率、跨项目隔离
◆
分轨不分裂： 两套评估共用 TraceEvent v0、沙箱、adapter 协议与报告骨架； 任务集、评分器、gate 阈值各自独立。butler-eval 先跑“规则 shadow”， 再跑真实 Agent；task-eval 继续复用现有 capability / repo 套件。 butler 轨已落地 11 条 fixture 用例（路由、/new、状态、 文本/卡片审批、Agent 回退、画像召回、Agent 派单、指代追问改写、 约束跨轮注入、无关轮次不注入），命令 pnpm eval:butler （runtime wfxm-butler，驱动 scripts/eval/run-butler.mts，当前 11/11 通过）； gate 同时跑 baseline（34 条，要求 100%）与 butler 轨 （要求 ≥ 90%），两者任一不达标即退出非 0。 用户可见消息另有结构断言：fixture 可声明 userMessage.mustMention / mustNotMatch / maxLength， butler 轨默认校验「无 markdown、无原始工具名、单条 ≤ 1800 字符、非空」。
闭环关键点：评分由「断言（是否做到）+ 轨迹（是否乱来）+ 成本/时延（是否划算）」三部分组成， 避免只看最终回复导致的“侥幸通过”。
◆
工具链外挂（详见 09）：Langfuse 承载轨迹 / 数据集 / 人工反馈， DeepEval 提供 Agent judge，Ragas 提供 RAG 检索与忠实度指标； 自研 verifier 仍是 gate 的唯一真值来源。

自动层（每次提交）

单元测试 + fixture LLM acceptance + 任务集回归。门禁：pass@1 不低于基线，成本与 P95 不显著劣化，禁止工具调用不得出现。

人工层（每周 / 按需）

复核队列只喂三类样本：低分、自动评分与人工判断冲突、新出现失败。每类给出归因选项， 避免开放式“感觉不对”。

改进层（提案制）

每个改进是带 owner、影响面、回滚开关的提案；合并前必须附同题复跑结果， 失败样本自动进入回归集。

数据集分层（L0–L4）

单一任务集无法同时回答“没坏”和“变好”。按目的分层，逐层扩大样本量与真实性； 只有 L2 以上计入能力结论，L4 提供线上外部效度。

08如何证明“能完成大部分开放性任务”

架构图描述的是能力边界，不是证据。把“大部分”转成可检验的命题： 先定义口径，再分层抽样，最后用置信区间、外部锚点与线上成功率交叉验证。

STEP 01 · DEFINE

先把“大部分”定义清楚

按能力维度加权计算通过率，建议门槛 ≥ 80%，并同时报告 pass@1 与 pass^k（k=3）；不报告单点的“100%”。

STEP 02 · SAMPLE

样本量与分层要够

单层 60–100 条才能把 95% 置信区间压到 ±10%；能力维度每维 ≥ 30 条， L3 repo-task ≥ 30 条，另设不参与调参的 held-out 集。

STEP 03 · VERIFY

交叉验证，避免自证

自建任务（内部效度）+ 公开基准（外部锚点）+ 线上成功率（真实分布）， 三条证据同时成立，结论才站得住。
