## 工作内容

### R8.x.9 candidate 2 — live e2e test of subagent→WS push

The R8.x.8 `ws-routes-e2e.mjs` only verified handshake + ping/pong
(not a real subagent reply). This card closes the live end-to-end
gap by adding a new script that drives the full pipeline:

1. `POST /v1/wechat/inbound` with a "delegate" task → 201 +
   `conversationId` + a parent reply that mentions "委派".
2. WS client opens `ws://127.0.0.1:3002/v1/ws?conversationId=<id>`
   **after** the HTTP response is back. (The /v1/wechat/inbound
   handler is synchronous-ish — the parent butler loop completes
   before HTTP returns, but the subagent reply is written by the
   polling worker ~5s after the request lands.)
3. Subagent worker fires `AssistantMessageProduced` → server calls
   `pushEventToSubscribers(parentConversationId, event)` → WS frame
   `{kind:"event", conversationId, event:{eventType,event,eventId}}`
   arrives at the client.
4. Test exits 0 if any frame contains the
   `AssistantMessageProduced` marker, 1 if no event within 30s, 2
   on fatal runtime error.

### Files changed

- `scripts/cutover/ws-subagent-push-e2e.mjs` (new, 218 lines)
  - HTTP path: `curlJson` with `-w "\n%{http_code}"` so we capture
    the status (201 expected, not 200 as the task draft suggested).
  - WS path: resolves `ws` via `createRequire` against
    `apps/api/package.json` (same pattern as R8.x.8
    `ws-routes-e2e.mjs`).
  - Detection: looks for both `AssistantMessageProduced` AND
    `"kind":"event"` so the test doesn't false-positive on a
    stray marker in an unrelated log line.
  - Hard timeout: 30s, ample for the 5s subagent worker tick +
    LLM call.
  - Exit codes: 0 = pass, 1 = pre-flight check failed / no event,
    2 = fatal runtime error (same convention as `ws-routes-e2e.mjs`).

### E2E actually verifies subagent→WS (self-review)

The test is **not** just a handshake smoke. It exercises:
- HTTP → WS conversationId seam (the seam the task brief worried
  about: `conversationId` is generated server-side in
  `/v1/wechat/inbound` response, so the WS client must connect
  **after** receiving the HTTP reply).
- Subagent worker poll → LLM call → reply write to parent stream
  → `pushEventToSubscribers` fan-out (the only way the WS frame
  arrives is if the subagent worker actually wrote the event and
  the WS push function was called).
- Frame envelope integrity (`{kind:"event", conversationId, event}`)
  matches the contract documented in `ws-routes.ts`.

To prove the test isn't passing by accident, the detection
function requires both `AssistantMessageProduced` AND
`"kind":"event"` substrings — a stray log line with the marker
alone wouldn't trip it.
