## 工作内容

### R8.x.10 — capability execution guard

Picked up from `docs/architecture/v5-r10-handoff.md` §8.2 and shift
032's next-item #3: R8.x.9 only gated capability *declaration* at
enqueue. The worker then called the child LLM with **no tools**, so
granted names like `get_current_time` were never used, and a child
that *did* emit a native `tool_call` would not have been blocked.

Three pieces:

1. **`capability-guard.ts`** — `normalizeCapabilityNames` accepts both
   `string[]` (R8.x.9 direct enqueue tests) and `{tool: string}[]`
   (`delegate()` outbox payload). Previously the worker filtered with
   `typeof c === "string"`, which silently dropped every real
   `delegate()` grant set to `[]`. `isToolCallAllowed` treats `general`
   as language-only. `llmToolsForCapabilities` intersects grants with
   `WEIBUTLER_LLM_TOOLS` (so `read_file`/`run_command` stay reserved
   until they exist).

2. **Child tool loop in `subagent-worker.ts`** (max 3 iterations) —
   advertises only granted tools; on each `tool_call` checks the
   guard *before* `findTool`/`runTool`; denied calls return
   `[error] capability denied: <name>` and write a `rejection` audit
   row with `toolName`; granted calls run via `runTool` and write
   `kind: "tool_call"`.

3. **`AuditEntry`** — added `kind: "tool_call"` and optional
   `toolName`. Existing delegation/completion/rejection rows unchanged.
